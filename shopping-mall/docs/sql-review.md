# SQL 적용 검토

> 이 문서는 **수정 전 SQL**의 검토 기록입니다. 이후 기존 ERD 기준으로 SQL을 수정했습니다. 현재 구조와 실행 방법은 [SQL 적용 안내](sql-application.md)를 참고하세요.

[문서 목록](README.md) · [기존 ERD](erd.md) · [테이블 정의](table-definition.md)

## 결론

`sql/schema.sql`과 `sql/seed.sql`은 **최소 쇼핑몰의 출발점으로 사용할 수 있습니다. 다만 기존 ERD를 그대로 구현한 SQL은 아닙니다.**

장바구니와 주문 통합, 직접 회원 인증, 결제 시도별 기록이라는 다른 설계를 채택했습니다. 이 구조 자체가 잘못된 것은 아니지만, 적용하려면 백엔드와 설계 문서도 같은 기준으로 맞춰야 합니다.

권장안은 **기존 ERD를 유지하고 SQL을 맞추는 방향**입니다. 이미 만든 ERD·구매 시뮬레이션과 일관되고 Supabase Auth를 활용할 수 있습니다. 테이블 수를 5개로 줄이는 것이 우선이라면 현재 SQL의 통합 장바구니 방식도 선택할 수 있습니다.

이번 검토는 파일 정적 분석입니다. 실제 Supabase에 SQL을 실행하거나 데이터베이스를 변경하지 않았습니다. SQL 문법 실행 검증·동시 구매 테스트·권한 테스트는 수행하지 않았습니다.

## 1. 두 파일의 역할

| 파일 | 내용 | 판단 |
|---|---|---|
| [schema.sql](../sql/schema.sql) | 회원·상품·주문·주문 항목·결제 5개 테이블, 제약·인덱스·접근 차단 | 기본 구조로 사용 가능. 인증·주문 전환·결제 확정 처리 추가 필요 |
| [seed.sql](../sql/seed.sql) | 상품 5개와 재고 등록. 품절 상품 1개 포함 | 초기 상품 조회·품절 표시 확인에 적합 |

스키마는 신규 프로젝트용입니다. 기존 동명 테이블이 있으면 오류가 발생하므로 기존 ERD로 만든 DB에 추가 실행하는 마이그레이션 파일로 사용할 수 없습니다.

시드의 `ON CONFLICT (id) DO NOTHING`은 같은 ID의 상품을 덮어쓰지 않습니다. 재실행해도 판매 후 재고를 초기화하지 않는 장점이 있지만, 시드에서 상품명을 수정해도 기존 행에는 반영되지 않습니다.

## 2. 기존 ERD와 달라지는 부분

| 항목 | 기존 ERD | 현재 SQL | 적용 영향 |
|---|---|---|---|
| 회원 인증 | Supabase Auth와 users 프로필 | users에 email·password_hash 저장 | FastAPI에서 비밀번호 검증·세션·로그아웃 등을 구현해야 함 |
| 장바구니 | cart_items 별도 테이블 | orders의 cart 상태 + order_items | 장바구니 API와 주문 전환 로직 변경 |
| 주문 상태 | pending / paid / cancelled | cart / pending / paid | 현재 SQL은 취소 상태를 허용하지 않음 |
| 결제 관계 | 주문당 최대 1행, 실패 후 갱신 | 주문당 여러 시도, 성공은 최대 1행 | 재시도는 INSERT. 성공 금액을 계산할 때 실패 행 제외 |
| 결제 상태 | pending / succeeded / failed | success / failed | 처리 중 상태를 저장하지 않는 결과 이력 모델 |
| 탈퇴 | 회원 삭제 후 주문 회원 ID=NULL | deleted_at 소프트 삭제 + 회원 삭제 RESTRICT | 탈퇴 이후 로그인·API 차단과 개인정보 정리 필요 |
| 상품 | image_url·is_active 있음 | 두 컬럼 없음 | 상품 이미지·판매 중지 기능 보완 필요 |
| 금액 | bigint | numeric(..., 0) | 원화 정수 표현에 사용 가능. JSON 응답 타입을 명시적으로 통일 |

## 3. 잘 설계된 부분

- PK·FK·필수값·양수 수량·음수 재고 방지 제약이 있습니다.
- 회원별 cart 상태 주문을 최대 하나로 제한합니다 (`schema.sql:66`).
- 동일 주문의 동일 상품 중복을 막습니다 (`schema.sql:79`).
- 주문 시점의 상품명·단가를 저장할 컬럼이 있습니다. 주문 확정 시 값을 고정해야 실제 이력 보존이 됩니다.
- 한 주문의 성공 결제는 최대 하나입니다 (`schema.sql:103`). 실패 기록을 남기면서 재시도할 수 있습니다.
- 주문 전환 이후 배송정보·주문 시각·양수 총액을 요구합니다 (`schema.sql:50`).
- 스키마 생성과 시드 입력을 각각 BEGIN/COMMIT으로 묶었습니다. 이는 설치 작업의 트랜잭션이며, 이후 구매 API의 트랜잭션을 대신하지는 않습니다.

## 4. 구현 전 해결해야 할 사항

### 우선순위 높음 — 주문·결제·재고의 원자적 처리

**근거:** `schema.sql:118–119`는 후속 API에서 보장한다고 설명하지만, 관련 DB 함수·트리거는 없습니다.

현재 제약만으로는 아래 상태를 막지 못합니다.

- 주문 총액은 29,000원인데 항목 합계는 24,000원인 상태
- 주문금액과 성공 결제금액이 다른 상태
- 성공 결제는 있는데 주문은 pending인 상태
- 재고 1개를 두 회원이 동시에 구매하는 상황에서의 잘못된 처리

해결은 모의 결제 확정 함수에서 주문과 상품을 잠그고, 소유권·상태·금액·재고를 확인한 뒤 재고 차감·결제 기록·주문 완료를 함께 반영하는 것입니다. 상품 잠금 순서는 일정하게 유지해야 합니다.

Supabase API를 통한 여러 `.execute()` 호출을 순서대로 실행하는 것만으로는 하나의 트랜잭션이 되지 않습니다. DB 함수 RPC 또는 직접 PostgreSQL 연결의 명시적 트랜잭션이 필요합니다. [Supabase 데이터베이스 함수 문서](https://supabase.com/docs/guides/database/functions)

성공 결제 UNIQUE 제약은 중복 성공 행을 막지만, 별도 요청으로 먼저 반영한 재고 차감까지 되돌려 주지는 않습니다. 중복 요청에는 기존 성공 결과를 반환하도록 구현해야 합니다.

### 우선순위 높음 — 인증 방식과 서버 권한 검증

**근거:** `schema.sql:5–19`, `schema.sql:106–114`.

현재 users.id는 독립 UUID이며 Supabase Auth와 연결되지 않습니다. Supabase Auth 토큰의 사용자 ID를 그대로 orders.user_id에 사용하는 구현은 이 스키마와 맞지 않습니다.

선택지는 다음 두 가지입니다.

1. 권장: 기존 설계대로 Supabase Auth를 사용하고 users는 프로필 테이블로 수정합니다.
2. 현재 SQL 유지: 안전한 비밀번호 해시 생성·검증, 로그인 시도 제한, 세션 만료·무효화, 탈퇴 계정 차단 등을 FastAPI에 구현합니다. `password_hash`가 비어 있지 않다는 CHECK만으로는 안전한 해시 사용을 보장하지 않습니다.

SQL은 anon/authenticated의 테이블 권한을 회수하고 RLS 정책도 만들지 않습니다. 따라서 일반 사용자 JWT로 테이블을 읽는 기존 설계는 그대로 작동하지 않습니다. 공개 상품 목록도 FastAPI를 거쳐야 합니다.

서버가 service_role 권한으로 접근한다면 각 API가 로그인 회원과 주문 소유자를 반드시 검증해야 합니다. 이 권한은 RLS를 우회하므로 RLS 활성화만으로 회원별 접근이 보장되지는 않습니다. [Supabase 공식 보안 설명](https://supabase.com/docs/guides/getting-started/the-supabase-way-to-build)

### 우선순위 높음 — 장바구니에서 주문으로 전환할 때 가격 재계산

**근거:** `schema.sql:38`, `schema.sql:70–82`.

order_items는 장바구니와 주문 항목을 겸합니다. 장바구니에 담을 때 12,000원이던 상품이 15,000원으로 변경되었는데, 주문 전환 시 단가를 갱신하지 않으면 오래된 가격으로 결제될 수 있습니다.

`cart → pending` 전환 시 현재 상품 가격·판매 상태·재고를 다시 확인하고, product_name·unit_price·total_amount와 배송정보·ordered_at을 함께 갱신해야 합니다. 가격 변경이 있으면 결제 전에 사용자에게 안내합니다. pending 이후에는 항목과 금액을 고정합니다.

CHECK는 현재 행의 값만 제한합니다. paid 주문을 cart로 되돌리거나 결제된 항목을 수정하는 행위까지 막는 상태 전이 규칙은 없으므로 서버 또는 DB 함수가 별도로 제한해야 합니다.

### 우선순위 중간 — 상품 화면·탈퇴·취소 정책

- **상품 이미지·판매 여부:** products에 image_url·is_active 추가를 권장합니다. 현재는 재고가 0인 품절과 판매 중단을 구분할 수 없습니다. 주문·장바구니에서 참조한 상품은 삭제도 제한됩니다.
- **탈퇴:** deleted_at을 기록하는 것만으로 기존 세션은 차단되지 않습니다. 모든 보호 API가 탈퇴 여부를 검사하고 세션을 무효화해야 합니다. 이메일 UNIQUE 때문에 탈퇴 이메일의 재가입도 기본적으로 차단되므로 재가입 정책이 필요합니다.
- **주문 취소:** cancelled가 허용되지 않습니다. 기존 설계의 미결제 주문 취소를 유지한다면 상태 CHECK와 배송정보·시간 CHECK도 함께 수정해야 합니다. 단순히 상태 목록만 늘리면 기존 checkout CHECK에 의해 취소 전환이 거부될 수 있습니다.
- **실제 결제:** success/failed 결과만 기록하는 모델은 모의 결제에는 사용할 수 있습니다. 실제 PG에서는 처리 중·확인 대기·제공자 거래 ID·멱등성 처리가 추가로 필요합니다.

### 운영상 주의 — 구매 내역 필터와 수정 시각

장바구니도 orders의 행이므로 내 주문 목록은 `status <> 'cart'`, 실제 구매 내역은 `status = 'paid'` 등 목적에 맞게 필터링해야 합니다. 정렬에는 담기 시각인 created_at보다 실제 주문 시각 ordered_at이 적합합니다.

updated_at 자동 갱신 트리거는 없으며 SQL 주석대로 각 UPDATE에서 명시적으로 갱신해야 합니다. 결제 시도 행의 created_at은 시도 기록 시각이고, 결제 완료 시각은 orders.paid_at입니다.

## 5. 현재 SQL을 선택했을 때의 구매 예시

시드의 데일리 머그컵 2개와 에코백 1개를 구매한다고 가정합니다. 총액은 12,000 × 2 + 15,000 = 39,000원입니다. ID는 설명용 별칭입니다.

| 단계 | 처리 | 결과 |
|---|---|---|
| 1. 로그인 | users에서 회원 확인, 직접 인증 세션 생성 | 탈퇴 회원은 거부 |
| 2. 담기 | orders O1을 cart로 생성, order_items 2행 생성 | 머그컵 2개·에코백 1개, 재고 유지 |
| 3. 주문 | O1을 pending으로 전환 | 최신 가격·배송정보·ordered_at·총액 39,000원 저장 |
| 4. 결제 실패 예시 | payments에 failed 행 INSERT | 실패 사유 저장, O1은 pending, 재고 유지 |
| 5. 결제 재시도 성공 | 새 payments 행을 success로 INSERT | 같은 트랜잭션에서 O1=paid·paid_at 저장, 머그컵 15→13·에코백 20→19 |
| 6. 다음 장바구니 | 새 orders O2를 cart로 생성 | O1은 구매 내역, O2는 새 장바구니 |

이 방식에서는 기존 cart가 주문으로 전환되므로 **결제 후에도 같은 장바구니 항목을 유지하는 기존 시뮬레이션과 다릅니다.** 선택 상품만 주문하거나 바로 구매할 때 기존 장바구니를 보존하려면 새 pending 주문으로 항목을 복사하는 등 추가 규칙이 필요합니다. 모든 항목을 한꺼번에 주문하는 흐름이 가장 단순합니다.

## 6. 적용 판단

| 질문 | 답변 |
|---|---|
| 기본 쇼핑몰 구현에 쓸 수 있는가? | 가능. 자체 인증·통합 장바구니 설계로 구현하는 경우 |
| 기존 ERD와 그대로 호환되는가? | 아니요. 인증·장바구니·결제·탈퇴 구조가 다름 |
| SQL 실행만으로 안전한 구매가 완성되는가? | 아니요. 소유권·가격 재계산·트랜잭션·중복 처리 구현 필요 |
| seed.sql은 활용 가능한가? | 가능. 이미지·판매 상태 컬럼 추가 시 기본값 또는 시드 보완 필요 |
| 권장 방향은? | 기존 ERD를 기준으로 SQL을 정렬하고, 시드 상품과 유용한 제약·인덱스는 활용 |

검토 결과만 작성했습니다. 원본 SQL·ERD·이미지는 변경하지 않았습니다.
